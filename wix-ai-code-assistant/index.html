Case study · Wix Studio · 2025

Making AI code safe for people who don’t code.

An AI assistant inside the Wix Studio editor writes custom code straight into live client sites. People were opening it, looking, and leaving. I found the four moments where trust was won or lost, and redesigned each one so the person stays in control of every change.

My role
Senior Product Designer, design lead for the assistant
I owned
User research, UX and UI, the AI’s behavior rules
Worked with
A product manager, an engineer, a BI analyst
Platform
Wix Studio, Velo (Wix’s code layer)

The problem

Only 45% of people who opened the assistant sent a single message. In interviews, one failed attempt was enough to stop people coming back.

What I did

Moved help to where people already work, replaced the blank chat with a first step, let code apply instantly with undo, and rewrote how errors are explained.

What happened

In an 18-day A/B test, new users who had the assistant published live code more often: 4.8% vs 3.8% without it.

01 / Context

The AI could write the code. People didn’t trust it enough to use it.

The assistant writes code straight into live client websites. For a designer who doesn’t code, one bad change can break a client’s site, with no obvious way back.

Constraints I designed around
Fixed placement

The product decision was that the chat had to live in the Velo code panel for now. So I couldn’t solve discovery by moving the panel. I had to bring entry points to the user instead.

Dev Mode dependency

The assistant only works with Developer Mode on. We switched it on in the background when someone opened the assistant, so people landed in a code environment they hadn’t asked for.

A short shelf life

A platform-wide Wix AI assistant was expected within about three months and might replace this one.

Hard technical edges

The way Velo displays files made writing code across several files difficult, and a slow first response delayed the assistant’s intro message. I took both to our engineer to find a way around them.

02 / Research

Wix Partners build sites for clients, and don’t all write code.

I interviewed 7 Wix Partners in July and August 2025, and paired what they told me with usage data from 7,448 people who opened the assistant.

Primary focus

Designers

Design and client work, little or no coding. Code feels risky to touch.

Need: a result that works, without reading code.

“Code is so overwhelming to me… But now, with the AI tool, it’s becoming a lot more approachable.”

Web designer, Wix Partner

Secondary

Low-code users

Handle simple code like animations and CMS tweaks. Hand complex work to a developer.

Need: code that works the first time.

“The main thing that I need from the AI Assistant is that the code would work.”

Low-code user, Wix Partner

Secondary

Developers

Build complex, data-heavy sites. Compare the assistant with ChatGPT and other AI tools.

Need: speed, site context and results they can check.

“I want a reliable, efficient tool that provides the solution that I’m looking for.”

Experienced developer, Wix Partner

6 of 7partners named the same top need: the code has to work.
5 of 7asked for better error handling and a clearer picture of what the assistant can and can’t do.
51%of conversations opened without a message ended with the person closing the assistant as their very next action.
The insight

“When you try something and it didn’t work, it’s very hard to come back to it. You have this stigma that it doesn’t really work.”

Web designer who doesn’t code, Wix Partner

Trust was the product. People valued undo above almost anything else because it let them experiment without fear, and they lost trust in a single failed attempt. So I stopped treating this as a chat design problem and asked a different question:

How might we let people who don’t code add custom code to a live site, and feel in control of every change the AI makes?

03 / The work

Four moments where trust is won or lost.

I followed people from “I want this on my site” to “it’s live”, found where they dropped off, and redesigned each of those moments.

03.1Moment 1 of 4 · Finding help

Help where you’re already working

What I saw

80% of conversations started from the right-click menu or the element’s Inspector panel, while someone was editing a specific element, not while thinking about code.

The choice

Since the chat had to stay in the code panel, I couldn’t make the panel easier to find. Instead I brought the way in to the element people were already pointing at, with that element passed in as context.

What the data said next

Intent showed in the numbers. About half of the conversations started from the properties and CSS panels led to added code, compared with about a quarter from the right-click menu. That made the case for more entry points where people are already working.

03.2Moment 2 of 4 · The first message

A first step instead of a blank box

What I saw

Only 45% of people who opened the assistant sent a first message. The empty chat was the biggest drop-off in the whole funnel. Of the people who didn’t write anything, half simply closed it.

Partners told me the same thing in their own words: they weren’t sure what to ask, or whether their prompt was good enough.

The choice

Open with ready-made requests instead of an empty box, drawn from what people ask for most. The top conversation subjects were styling and layout (32%), animations (16%) and event-based interactions (16%), and the suggestions follow them: show or hide an element on click, animate on hover, display CMS content, and style custom CSS.

Some people who skipped the chat went straight to coding by hand (about 10% of those conversations), so I added a clear way out for them: “Prefer manual coding?”.

How I’d measure itThis change targets the biggest drop in the funnel, so success is simple to read: more than 45% of people who open the assistant send a first message, without fewer of them going on to add code.
03.3Moment 3 of 4 · Applying code

Apply instantly, undo anytime

The first version asked people to review the code and then choose to add it. For a developer that’s a sensible gate. For a designer it’s a question they can’t answer: they can’t judge code, so the gate made them feel responsible for something they couldn’t see.

I moved the safety net to after the change. Code applies right away, with a plain-language summary, a preview, and a one-click restore.

Cards redrawn from the shipped design so the text is readable. The copy is unchanged.

Trade-off

Applying first means the AI sometimes changes something the person didn’t want. I accepted that because the alternative, a gate people couldn’t judge, was already stopping them. The cost had to be made cheap: every change is undoable, and nothing is lost.

Iteration

The first build of restore broke the promise. When I tested it in May 2025 I logged six problems for the team, including:

  • Every restore created a new version called “restored code”, whichever version you picked, so you couldn’t tell what you’d gone back to.
  • Restoring one version silently removed every change made after it.
  • After undoing AI code with restore, you could no longer get back to the version that had the code.
  • A restored version looked like any other version, so you could “restore a restore”.

The fixes became the history view: every change is dated and summarized, labeled as a code version with a description, with undo and preview always in reach.

03.4Moment 4 of 4 · When code breaks

When code breaks, say why and what’s next

Generic errors like “Something unexpected happened” made people give up. One designer said it felt like the assistant “kind of gave up on my request.” Each error now says what went wrong in plain words and offers one next step: retry, add a permission, or get support.

Behind the messages, I wrote the rules for when the AI should try to fix things on its own. The golden rule:

Only auto-fix if it’s obvious, reversible and safe. Otherwise, guide.

When the AI should not fix things by itself

  1. 1. Critical context is missingFor example, database credentials it doesn’t have. “I don’t have enough information to safely fix this. Let’s walk through it together.”
  2. 2. It would have to invent elements, IDs or filesAdding unknown elements can break layouts, and intent is unclear. “Before I add anything, let’s make sure this is what you want.”
  3. 3. The action is destructive or can’t be undoneDeleting data, resetting configuration, changing a schema. Explicit confirmation, or share with a developer.
  4. 4. It touches securityAPI keys, admin roles, access controls. “For security reasons, I can’t make this change automatically.”
  5. 5. The choice is subjectiveFade in from the left or the right? Version 1.2 or 2.0? “There are multiple ways to solve this. Want to see the options?”
What I’d changeThe first error still tells people to go to the Problems tab and fix it manually. That works for a developer, but it’s the kind of dead end my own research warned about for designers. The next version should offer a guided step, or a way to hand the problem to a developer.
04 / Outcome

More people changing code, and more code going live.

We ran an A/B test on new English-speaking users for 18 days: 5,422 without the assistant and 5,270 with it. Then we followed every step of the funnel after launch.

Share of new users who…Without assistantWith assistantChange
Changed their site’s code4.7% (255)6.3% (324)+34%
Published working code to their live site3.8% (209)4.8% (252)+27%
How to read this

The test compared having the assistant with not having it, so it measures the whole feature, not each design decision on its own. The funnel below is where I tracked individual moments.

Why not Dev Mode adoption

Opening the assistant could switch Developer Mode on behind the scenes, so a rise in Dev Mode users partly measures that switch, not people choosing to code. I report the two outcomes that need a real action: changing code and publishing it.

What surprised us

With the assistant, a slightly smaller share of Dev Mode users went on to change code (43.9% vs 48.0%). More people were arriving in Dev Mode who hadn’t chosen to code. Looking at the step that matters for them, sending a message, 49% went on to change code. That pointed us back to the first message.

Once people sent a first message, 75–82% moved on at every step. The real drop was the empty chat, which is why the next round focused on that first step.

What people asked for changed

After rollout, styling and layout became the top subject, up from 19% to 32% of conversations. People were bringing smaller, everyday design tasks, not only “real code” jobs. That’s the audience we designed for.

05 / What’s next

What the research told us to do next

Solve it without code when possible

Partners asked the assistant to point them to existing Wix features (like data binding) before writing code. Code should be the last resort, not the first.

Make AI code traceable

“I want to see AI-applied code in a different color, so I can remove it if needed without breaking other things.” Group, label and roll back AI changes as a unit.

Match tone to skill

Beginners found developer jargon intimidating. Let people set their comfort level once, and adjust language and detail to it.

In their words

“I want to take baby steps with it just because code is so overwhelming to me and intimidating to a certain degree. But now, with the AI tool, it’s becoming a lot more, I guess, approachable.”

Web designer who doesn’t code, Wix Partner
